# Architecture

## Goals

- Local-first planning on the PC, with a read-only mobile export planned later.
- The attraction library must be self-contained when used offline. Source URLs
  are provenance links for optional later browsing, never runtime dependencies.
- Keep browser presentation, HTTP routes, catalog validation, and data access in
  separate modules.
- Keep route calculations deterministic and separate from optional Claude
  workflows.
- Treat researched attraction information as evidence-backed user data:
  source references and image usage rights travel with each record.
- Preserve a review gate: discovery candidates are not approved catalog items.

## Initial structure

- `app.py` is the development entry point.
- `hainan_cycling/` contains application code. `catalog/` owns catalog schemas
  and persistence; `web/` owns Flask routes.
- `templates/` and `static/` contain the web presentation layer.
- `data/attractions.json` is a local, readable catalog. User-added image files
  belong under the ignored `data/media/` directory.
- `tests/` covers schemas and HTTP behavior.
- `docs/` records product decisions and source/review requirements.

## Attraction data lifecycle

`candidate` → `under_review` → `approved` or `rejected`.

An attraction carries independently sourced positive and negative experience
claims, linked to source records. Representative and additional images retain a
source link plus rights metadata. Local copies are valid only for authorized
downloads or user uploads. Missing coordinates and limited research are
represented explicitly instead of being filled with guesses.

## Offline content contract

- Store the attraction name, coordinates, category, original-language summary,
  experience notes, and selected image files locally so the catalog remains
  useful without network access.
- Keep source platform, author when available, date, title, and URL as
  provenance metadata. Opening a provenance link is an optional online action;
  no attraction details should need to be fetched from the source page at
  display time.
- Include an image in an offline catalog/export only if it is user-provided or
  its license explicitly permits the intended local copy and redistribution.
  Retain creator, license, and source-page attribution with the image.
- Do not use YouTube API responses as the content store for offline attraction
  summaries or images. Search APIs may be evaluated separately as optional
  discovery tools, subject to each provider's current terms.
- The future mobile export must contain the selected attraction records and
  permitted local images, not merely links to online pages.

## Planned boundaries

- Map rendering and routing adapters will remain separate from attraction
  catalog code.
- Route distance, segment metadata, and GPX serialization will be calculated
  by deterministic application code, not generated by an LLM.
- Claude Code integration, if added, will propose structured changes through
  application services; it will not directly edit canonical catalog files.
- The mobile handoff is a read-only, self-contained offline export, not a
  second planning application.

## Reference adaptation

The requested Family-Accounting-Web-UI reference was inspected for its
organization of a Flask entry point, templates, static browser assets, and
separated modules. Those structural ideas are adapted here; its code, domain
logic, and presentation are not reused.
